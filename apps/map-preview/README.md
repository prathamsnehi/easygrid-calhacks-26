# California valley site planner

Interactive voxel map for fictional parcels, A/B facility placement and cost-optimized transmission connections (CAL-7/CAL-8), with participant registration, affected-parcel analysis and a user roleplay handoff (CAL-23). After registering the demo participant, the user places a substation and data center; the planner calculates feasible support-to-support routes and renders the recommended route with lattice pylons and sagging conductors. The analysis packages the selected route and owner proposals for Pratham's integration. Calls, agreements and payments remain separate backend steps.

**Product language: always English.** Keep every map label, message, accessibility description, fixture display value and routing explanation in English. The language regression checks cover source files and the generated deliverables.

Use Node 24, matching the map CI. Run these commands from the repository root:

```sh
npm ci --ignore-scripts --prefix packages/contracts
npm run build --prefix apps/map-preview
npm test --prefix apps/map-preview
npm run dev --prefix apps/map-preview
```

Open `apps/map-preview/dist/index.html` directly for an offline standalone preview, or use the local server at `http://127.0.0.1:4177`. The standalone preview makes no external requests; source links and an optional registered host integration are explicit actions. `dist/parcel-fixtures.json` contains the generated parcel and owner records. Installing the shared contract dependencies enables the handoff compatibility tests; the map build itself has no external dependencies.

The **Start demo** screen requires the participant's name, phone number and explicit consent to an AI roleplay demo call before planning is available. US 10-digit numbers automatically receive `+1`; an 11-digit number starting with `1` is also accepted. Explicit international country codes are preserved. The private participant phone is normalized to `+` and digits. Select **Start demo** after all three are valid to unlock the map. Registration stays local: it does not invoke the host callback or place a call.

Click a valid location to place A (substation, 12×10 tiles), then B (data center, 20×14 tiles). The ghost and footprint turn green or red; the card explains rejection. Every footprint cell must be flat, vacant and inside the map, and the two facilities cannot overlap. The A/B buttons and building labels allow repositioning; old placement stays until a valid replacement is confirmed. The reset button clears the plan and participant details, then returns to **Start demo**.

The **Parcels** button shows property boundaries and fictional owner/contact/price details. Hover previews a parcel; clicking selects it and fits its full land bounds into the map area beside the information card. That selection stays fixed while hovering or panning until another parcel is clicked. **Show on map** restores the selected parcel's framing. **Find open site** and **Place here** provide an alternative to mouse placement and support keyboard use.

After registration and placement of both facilities, a queued route calculation runs automatically. **Transmission** opens the comparison panel. Select an alternative to update its pylons, conductors, cost breakdown and affected parcels together. Changing a committed facility immediately removes the old network, restores its crop clearings, and calculates a new connection. Reset cancels queued work; reload restores only validated saved endpoints and requires participant registration again before recalculating the recommendation. An infeasible connection is reported without relaxing constraints or showing a stale network.

Choose **Analyze affected parcels** to open **Land & compensation**. Each row shows the recommended offer and negotiation limit. Select a parcel for its owner, land use, wire length, towers, monthly fee and status; **View breakdown** expands the calculation. The recommendation is the selected route's allocated line and foundation allowance. The negotiation limit is 120% of that recommendation, rounded down to cents; counteroffers do not change the starting basis. Monthly rent stays separate. See [Offer policy](../../docs/OFFER_POLICY.md).

The parcel totals reconcile to the selected route's compensation and rent. A pylon whose pad touches several parcels appears in each parcel's impacts; the route's pylon total remains a unique count. Corridor-only parcels without a priced line or foundation impact show **Review required** and block negotiation readiness. Their zero allowance is not an evaluated offer. Monthly rent is a rounded equivalent; the full-horizon amount is authoritative.

Land records use a compact right sidebar on desktop and a bottom sheet on mobile, with other information panels hidden while analysis is open. Selecting a row or **Show on map** fits the full parcel into the unobstructed map area, accounting for the actual panel bounds and current camera angle. Resizing reframes the selected parcel; narrow landscape layouts retain a side panel when a bottom sheet would leave too little map space.

**Continue to contract & settlement** starts disabled. The manual **Simulate refusal** journey enables it after an eligible bypass and assumed acceptances by the other fictional owners; clicking opens a local preparation summary without making a payment request. In host-connected mode, a matching host approval and connected settlement handler are still required to submit the first simulated settlement. Route or participant changes revoke readiness. See [Settlement UI integration](../../docs/SETTLEMENT_UI.md).

## User roleplay and Pratham handoff

The first valid route assigns the participant registered on **Start demo** to one affected parcel. The assignment prefers a pylon-bearing parcel, then the greatest crossed length. The original owner/parcel stays fixed for that page session, including when a replacement route excludes it. A confirmed refusal locks further live calls. This is a display and handoff overlay: the underlying fictional parcel and owner records are not rewritten. Reset starts a new session; database-backed restoration and the planned seeded-random assignment remain separate integration work.

**Simulate refusal** runs the post-call demo without placing a call: exclude the original parcel, find one eligible alternative, compare the old/new route and cost, and obtain explicitly simulated acceptances from every other final-route owner. The resulting agreement-preparation packet does not create signatures, manager approval or payment. Host applications can deliver validated results through `setNegotiationSource` / `applyNegotiationUpdate`; see [Post-call routing](../../docs/POST_CALL_ROUTING.md) for the canonical result mapper, condition handling and pending SpacetimeDB integration.

Call consent is separate from land-access consent, which remains pending. Personal name and phone data are held only in page memory, never written to local storage or fixtures. **Edit participant**, available from the toolbar or participant summary, returns to the registration screen and invalidates any pending handoff. The endpoints are preserved, but planning, routing and public handoff access stay locked until the participant is validated again with **Start demo**. **Reset plan**, reloading and `pagehide` clear participant details and require registration again. Reload can still restore validated A/B coordinates independently.

**Agent call** is the single action for sending the selected route and private participant details to the connected calling agent. It stays disabled until the route is eligible, registration and consent are valid, and a host handler is connected. There is no JSON download control. The app blocks duplicate requests while pending and after the handler accepts the request; changing the participant or route invalidates the previous request.

The host registers a handler through `window.easygridDemo.setHandoffHandler(handler)` and may inspect a contact-redacted packet with `window.easygridDemo.getHandoff()`. `getHandoff()` returns `null` until both a validated participant and a current selected route are available. Only **Agent call** sends `{handoff, participant, signal}` to the handler; **Start demo** does not. A resolved callback means the agent accepted the request, not that a phone connected. The standalone preview has no calling agent configured. The host must supply backend project/parcel IDs and revisions, private contact registration and the voice integration, and respect the abort signal on participant or route changes. The map adapter packet is version 2 with `userRole`; the nested shared API contract remains version 1. Read [PRATHAM_HANDOFF.md](../../docs/PRATHAM_HANDOFF.md) for the integration sequence.

## Map controls and fixtures

One-finger drag or ordinary primary-button mouse drag pans. Two-finger drag rotates and tilts; pinch distance still controls zoom during that gesture. Shift-drag or right-drag also rotates and tilts. Scroll or pinch to zoom up to 5× the overview. Keyboard: arrows rotate, Shift+arrows pan, +/− zoom, 0/Home reset the view, 1/2 select A/B, Enter confirms a preview, Escape leaves placement mode. Double-click no longer resets the camera, so it cannot conflict with placement clicks. Pointer drags and pinch gestures do not place buildings.

The A/B plan is saved in this browser's local storage when available; participant registration is not. Reloaded coordinates are validated again against the current fixture; all parcel IDs, heights and connection points are rebuilt. The startup gate remains closed until new participant registration succeeds. Storage failure is reported without preventing placement after registration. Local file URL storage support depends on the browser.

The valley is 120 × 96 tiles (four times the original 60 × 48 area). Six empty 22×16 clearings provide space for 20×14 footprints. Tile dimensions and facility sizes are demo design choices, not an engineering scale or siting approval.

`parcels.js` assigns every tile to one of 24 fictional properties L001–L024 and one synthetic owner O001–O024. Farm field IDs P1–P6 are retained separately as `fieldId`. Parcel polygons follow the clipped map outline, and their area is measured in tiles. Phone displays are mock values with `dialTarget:null`; emails use `example.com`. Prices in the map's general parcel inspector are fictional whole-parcel starting offers in USD cents; the analysis screen instead uses route-specific compensation. Neither is an appraisal. No user phone number is embedded in the source or exported fixtures; private participant binding is separate from synthetic ownership.

The source is split into `world.js` (terrain and occupancy), `parcels.js` (property fixtures), `landscape.js` (voxel terrain and reversible crop clearing), `facility-models.js` (buildings), `placement.js` (site validation, picking and saved plans), `planner.js` (placement/inspection UI), `routing.js` (support graph and optimization), `transmission-models.js` (pylons and conductors), `route-controller.js` (route state, comparison and redraw), `parcel-analysis.js` (affected parcels and reconciled costs), `handoff.js` (redacted contract snapshot and coordinate adapter), `analysis-controller.js` (analysis UI, participant memory and host handoff), and `main.js` (camera, lighting and pointer gestures). `index.html` and `styles.css` define the planner controls. The build wraps source modules separately and embeds Three.js in one HTML file.

Facility eligibility is separate from line-passage and tower-foundation checks. Farmland can support a transmission corridor and cleared tower pads, even though facilities require vacant meadow. These checks do not establish owner consent or regulatory approval. Map geometry uses explicit local demo coordinates. The handoff adapter converts them into synthetic WGS84 GeoJSON using an invented origin at longitude −120.5, latitude 37 and 25 meters per tile (coordinate adapter v2). That declared horizontal scale is shared by pricing and the handoff; it does not turn demo dimensions into surveyed geography or an engineering design. The optional owner-handoff offer policy is additive; API v1 remains compatible.

## Route model

The graph contains two front facility terminals and feasible tower sites on a 3-tile lattice. Every tower needs a flat 2×2 foundation. Water, riverbanks, roads, existing structures, tree crowns and rocks exclude foundations. Spans are at most 15 tiles long. Exact segment/rectangle intersections check a conservative 0.8-tile corridor, including corner contacts; they exclude structures, facility bodies, refused parcels and map boundaries. Facilities connect through their front service aprons.

Each support is 10 demo units high. Three conductors have a maximum modeled sag of 1.1 units and radius 0.045. Terrain and conservative vegetation/rock envelopes are checked for at least 2 units of clearance under the cable. These dimensions are demo choices, not voltage-dependent engineering standards. The physical layer follows the exact graph edges without smoothing through obstacles. Crop and grass instances intersecting tower foundations are hidden reversibly; soil, trees, buildings and underlying parcel metadata stay intact.

The balanced objective is additive integer USD cents: line construction + towers + two fixed endpoint supports + engineering/management + contingency + terrain/elevation + water/road/agricultural/vegetation impacts + parcel-specific land allowance + 12 months of simulated rent. Dijkstra finds the minimum of this objective on the declared graph. Per-edge/node amounts are rounded to cents before search, and the displayed breakdown reconciles to that same total. Parcel IDs are deduplicated; land allowances use traversed length and foundation area, not the whole-parcel opening offer in the inspector.

Distance-first and lower-impact searches supply alternatives. All alternatives are priced under the same balanced objective and identical paths are deduplicated. **“Lowest modeled cost” means optimal within this finite demo graph; it does not claim a global geographic optimum or a construction-ready design.** Unknown owner consent stays pending, `readyToApprove` is false, and explicit refusal blocks a route.

The 230 kV single-circuit estimate uses reported MISO MTEP24 component benchmarks, centralized in `cost-model.js`: $128,393 per installed tower allowance, $161,748 per endpoint support and approximately $76,055 per route km of installed wire. A 10% engineering/management allowance and 30% contingency on construction plus engineering are explicit demo choices; neither applies to land compensation or rent. See [cost basis and exclusions](../../docs/TRANSMISSION_COST_MODEL.md). The horizontal scale is 25 m/tile, making the existing maximum span 375 m; vertical geometry remains stylized. These are planning estimates, not current California quotes.

After both sites are placed, calculation begins promptly and the result is revealed after at least 1,600 ms total elapsed with a concise loading indicator. This is presentation timing, not extra AI reasoning. Slower computation can take longer. Editing sites, resetting or reopening participant registration invalidates pending results; reduced-motion preferences suppress the animation.

## Criteria references

- [Ironwood Routing Study, September 2025](https://ia.cpuc.ca.gov/environment/info/ecorp/ironwood/pdfs/Appendix%20K_Routing%20Study.pdf): CPUC-hosted applicant study weighing constructability, cost, land/ROW and environmental/land-use impacts. Its categories are project-specific, not statewide scoring weights.
- [PG&E Overhead Transmission Line Design Criteria, December 17, 2020](https://www.pge.com/assets/pge/docs/outages-and-safety/outage-preparedness-and-support/oh-transmission-068177.pdf): motivates checking sag and clearances; its engineering requirements are not implemented by the fictional dimensions above.
- [PG&E Easement and Property Requests](https://www.pge.com/en/about/land-use-and-sales/easement-and-property-requests.html): land rights remain separate from geometric feasibility.

## Verification

`npm test` builds the actual standalone output, then tests parcel coverage, placement and persistence, English-only output, weighted-path optimality against exhaustive small graphs, span/foundation constraints, route and parcel cost reconciliation, user assignment, handoff contract compatibility and contact redaction, conductor geometry/continuity/disposal, and UI state flows in a Node VM with real Three.js and a stub renderer. Those UI tests are behavioral checks; they do not establish browser layout, GPU performance or actual WebGL rendering.

Three.js 0.180.0 is vendored from the official npm package, with its MIT license, so the generated preview needs no external assets or runtime installation. All map objects are procedural geometry. The additive post-call mapping helper preserves shared API v1. Development follows the repository's [Linear/GitHub workflow](../../AGENTS.md); generated `dist/` files and private participant details must not be committed.
